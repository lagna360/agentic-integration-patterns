# Chapters 4–22 companion evidence: incremental governed-work slices

This module carries one teaching codebase forward. Chapter 4 contributes the first model-assisted Camel route, Chapter 5 adds the typed work envelope and admission rules, Chapter 6 adds a conditional Kafka-to-JDBC transport/inbox boundary, Chapter 7 adds governed artifact resolution plus an immutable context snapshot, Chapter 8 adds one read-only governed capability, Chapter 9 maps a validated advisory class through policy to fixed Camel targets, Chapter 10 runs two governed read investigations through a bounded Recipient List and immutable evidence reducer, Chapter 11 persists one run state machine with expected work, inbox, leases and fencing, deadline recovery, and an event outbox, Chapter 12 classifies trusted failure observations without scheduling retries, Chapter 13 records and reconciles one governed inventory-reservation effect, Chapter 14 adds a narrow application-owned next-attempt policy, Chapter 15 adds durable policy and human authority, Chapter 16 adds multi-effect recovery and compensation, Chapter 17 adds a protected route-security pre-gate, Chapter 18 adds independently operated remote-peer task ownership, Chapter 19 adds typed history views and an authorized zero-effect replay boundary, Chapter 20 adds a deterministic-fixture evaluation corpus and release-gate proof, and Chapter 21 adds a sealed deployment-boundary manifest plus bounded post-evaluation stage-promotion admission. Chapter 22 reuses anchored evidence from these slices; it deliberately adds no umbrella runtime.

It is intentionally a one-shot model-assisted workflow, not an agent and not a production deployment.

## Test the deterministic profile

From the repository root:

```shell
./mvnw -pl companion/order-exception-desk -am test
```

The default profile sets every Spring AI model family to `none`—chat, embedding, image, moderation, speech, and transcription—and sets `orderdesk.kafka.enabled=false`, so no provider key, broker, or Docker daemon is required after dependencies are cached. Tests cover the earlier route behavior plus envelope and schema admission, Kafka/inbox crash windows, artifact/context integrity, governed capabilities and routing, evidence aggregation, durable process recovery, failure classification, effect certainty, retry ownership, durable approval, multi-effect compensation, route security, remote-peer lifecycle, history/replay, the Chapter 20 evaluation slice, and the Chapter 21 deployment-boundary proof. The evaluation tests use deterministic candidate fixtures to verify exact, admissible-set, property, human-required, and unscorable outcomes; retained-input, corpus, output, and candidate digests; blocking structured-output/adversarial findings; per-case-and-dimension repeated-sample Wilson intervals; usage-source separation; and an owner-controlled comparison with exact pinned baseline and candidate versions. The deployment tests bind exact candidate, image, configuration, identity, typed state, consumer-group, role-specific Kafka partition ownership, lifecycle and ownership fields; reject drift; prove that replay/evaluation cannot acquire protected operational mutation or either target surface; separate effect mutation from observation-only recovery; and keep `orderdesk-candidate-20.1` blocked from staging, canary and production. A finding proves only what the deterministic fixture establishes; it does not prove that an operational policy, authorization, capability, firewall, orchestrator or effect gateway ran. H2 is an in-memory transaction/constraint proof, not a production durability, locking, identity-provider, or audit-system claim.

## Optional Kafka compatibility test

With Docker available, run the pinned `apache/kafka:4.3.1` broker through Testcontainers:

```shell
./mvnw -Pkafka-it -pl companion/order-exception-desk verify
```

The test enables the conditional Kafka route, sends the canonical command through a real Kafka client, and verifies the SQL inbox and consumer-group offset. The Kafka route remains off by default.

## Optional live profile

The `openai` profile activates the Spring AI adapter. Supply credentials through the process environment, never through an event or committed configuration:

```shell
export OPENAI_API_KEY=replace-with-a-real-secret
export OPENAI_MODEL=gpt-5-mini
./mvnw -pl companion/order-exception-desk spring-boot:run \
  -Dspring-boot.run.profiles=openai
```

The earlier workflow still exposes an in-process `direct:` input. The Chapter 6 Kafka consumer is a separate conditional adapter and is not enabled by the live AI profile unless explicitly configured.

## Deliberate limitations

The case store, audit and capability recorders, fixture identity binding, fixture artifact and inventory adapters, `direct:` inputs, SEDA outputs, approximate token estimator, narrow email masker, and H2 database are teaching substitutes. The Kafka slice demonstrates broker delivery plus a local inbox/disposition boundary. The context slice stores exact fixture bytes and a separately hashed model-safe view, but it does not implement production object storage, malware scanning, general de-identification, cache infrastructure, source-system snapshot transactions, encryption/key management, legal retention, or a durable worker that claims `admitted_work`. The capability slice does not implement MCP transport, OAuth, a secret manager, durable invocation records, distributed quotas, or tool idempotency. The routing slice does not implement a live classifier, calibrated score, durable work queue, dynamic registry, or manual-review process. The Chapter 10 slice remains an in-exchange, synchronous aggregation proof; Chapter 11 begins a separate durable process boundary around a closed evidence-set signal rather than retrofitting durability into that accumulator.

The Chapter 11 slice proves local transaction rollback, durable disposition of recognized evidence contradictions, required-work policy checks, compare-and-swap predicates, lease fencing, authoritative application-clock transition/deadline guards, and restart-style re-claim logic in one H2-backed JVM. Unexpected programming and database failures still propagate. The closed-evidence Camel seam is internal and already claimed; an external producer never supplies an owner or fence token. Its query-then-insert inbox can surface a concurrent unique-key race for retry. Its due-row scan and outbox relay are single-database teaching implementations, not production SQL Server/PostgreSQL locking, database-time claims, distributed clock, multi-relay, change-data-capture, broker-delivery, retention, migration, or capacity proofs. The relay is explicitly at least once and can republish the same event ID after a crash.

The Chapter 12 `direct:` route is also internal. Trusted gates or adapters construct its bounded observations; an external caller or model does not choose the category, destination, or retry eligibility. Its SEDA outputs are visible test destinations rather than durable work queues. The slice classifies only and delegates durable external-effect handling to Chapter 13.

The Chapter 13 effect command is an internal, already-governed teaching record, not a model tool request or public protocol. The fixture warehouse implements a deterministic idempotency contract solely for forced tests. The ledger proves local SQL transactions, immutable intent comparison, an optimistic/fenced dispatch claim, durable attempts and reconciliation observations, and conservative `UNKNOWN` recovery. It does not prove a real target's key scope, retention, consistency, authentication, availability, callback delivery, or exactly-once behavior. It implements no automated retry, backoff, breaker, approval process, compensation, production relay/CDC worker, distributed claim scan, archival policy, or multi-effect workflow. Its SEDA outputs are visible test destinations, not durable operator queues. The module also does not prove broker replication, production security, capacity, or production observability. Those omissions are documented rather than implied to be solved.

The Chapter 14 slice persists only accepted retry schedules and conservative per-candidate reservations; refusals and observed/unknown provider usage are not journaled or settled. A schedule row is not a shared run-, tenant-, or provider-wide budget, and its stored claim lease is not reclaimed by this slice. The Resilience4j breaker and semaphore capacity gate are process-local. The Camel route yields at most one permit per delivery but does not execute the adapter or structurally prevent a caller from invoking an adapter twice; the tests deliberately perform one fixture call. Effect tests prove policy eligibility/refusal and schedule identity only—they do not reopen the Chapter 13 ledger, invoke a second real effect, or prove target key retention. The local HTTP proofs do not cover proxies, meshes, transport retransmission, provider cancellation, or billing.

The Chapter 15–17 slices continue to use fixture policy, actor, protected provenance, resource, grant, and adapter state. They prove local binding, transitions, pre-gate ordering, reduced persistence, and zero handoffs for forced denials; they do not implement an identity provider, broker-side provenance service, policy distribution system, credential rotation, production row-level security, tamper-evident audit archive, legal retention workflow, distributed revocation, or incident-management platform. The Chapter 17 pre-gate hands permitted work to the already established authority/effect boundary; it does not replace that boundary or call the warehouse itself.

The Chapter 20 slice is an executable evaluation example, not a benchmark, model-training system, statistical certification, or claim that fixed fixtures predict production quality. It performs no live provider, tool, message, or effect call. Each 95% Wilson interval applies to one pinned case and quality dimension; heterogeneous cases are never pooled into one release score, and every scored pair must have an owner-supplied threshold and regression limit. Those intervals still do not establish sample independence or future performance. Human judgements bind the exact candidate digest, structured-output digest, case/sample, rubric, and reviewer-role reference, but this slice does not implement reviewer assignment, adjudication, inter-rater agreement, dataset governance, leakage detection, production drift monitoring, or a release deployment. Declared, locally counted, and reconciled usage sources remain separate rather than being treated as interchangeable cost truth.

The Chapter 21 slice is a deterministic responsibility-manifest and post-evaluation promotion-admission proof, not a container image, scheduler, cloud deployment, network-policy validator, secret manager, migration runner, capacity model, regional failover implementation, or release platform. Its enum sets stand in for enforceable capabilities, typed state grants, credentials, broker routes and network targets. Production controls must map those declarations to real workload identities, secret references, broker ACLs, datastore grants and egress policy and verify them independently. The recovery fixture distinguishes observation from mutation, but no real target API or credential issuer proves that distinction here. The manifest digest detects changed fields only while a protected owner preserves the approved digest; it is not a signature or proof of who sealed it. Promotion admission loads release evidence and stage authority by reference from an in-memory provider, refusing missing or fabricated references; production must supply authenticated, authorized and integrity-checked protected storage. The synthetic eligible candidate proves only the conditional post-evaluation stage sequence; it does not replace the canonical blocked release or authorize an external effect. No Docker, Kubernetes, cloud account, or external deployment service is required or exercised.
